# Аудит проекта GravityMD — Комплексная оценка качества и архитектуры

## Роль и контекст

Действуй как **Senior Software Architect** с экспертизой в:
- **Rust** (Tauri 2.x, tokio, системное программирование)
- **TypeScript / React 19** (функциональные компоненты, хуки, Vite)
- **Десктопные приложения** (IPC Frontend↔Backend, файловые ассоциации, мультиоконность)

Твоя задача — провести всесторонний архитектурный аудит кодовой базы внутри `<workspace>`. Мышление критическое, точное, без общих фраз. Указывай конкретные файлы, строки и технические причины.

---

## Универсальные ограничения (строго)

- **НЕ** модифицируй, не создавай и не удаляй файлы.
- **НЕ** предлагай полную перезапись кода. Описывай несоответствия и ссылайся на конкретные файлы/функции.
- **НЕ** используй размытые формулировки. Каждая находка: `файл`, `строка` (или функция/компонент), `конкретная техническая причина`.
- Весь анализ должен соответствовать экосистемам **Rust 2021 edition**, **React 19**, **TypeScript 6.x**, **Tauri 2.x**.

## Часть I: Микро-аудит — Качество кода и технический долг

### Вектор 1: Архитектурная чистота

Применительно к Rust (`src-tauri/src/lib.rs`) и TypeScript (`src/`):

- **DRY-нарушения (Rust)**: дублирование логики между командами (например, `read_file_content` / `write_file_content` / `write_file_binary` — общие паттерны обработки ошибок, нормализации путей `normalize_path`).
- **DRY-нарушения (TypeScript)**: дублирование логики обработки файлов между `handleOpenFile`, `handleOpen`, `loadContent`; повторяющиеся конструкции `toaster.add` с одинаковой структурой; дублирование логики парсинга в `handleExportDocx` и `handleImportDocx`.
- **Связность и разделение ответственности**: `App.tsx` (~664 строки) — монолитный компонент, содержащий всё: редактор, файловые операции, импорт/экспорт, тему, зум, About-диалог. Выделить возможности для декомпозиции на кастомные хуки (`useFile`, `useTheme`, `useZoom`) или отдельные компоненты.
- **Состояние редактора**: мультиоконная архитектура — проверить, нет ли гонки состояний между окнами (реестр `OpenFiles` в Rust vs кэш `currentFile` в React).
- **Типизация в Rust**: использование `String` для путей вместо `PathBuf` / `&Path`. Оценка необходимости `Mutex<HashMap<...>>` vs `DashMap` при конкурентном доступе.

### Вектор 2: Современные стандарты — Rust 2021 и React 19

**Rust:**
- Использование `if let Ok(...)` цепочек vs оператор `?` в функциях, возвращающих `Result`.
- `.lock().ok().and_then(...)` паттерны — можно ли упростить через `.lock().unwrap()` с пояснением безопасности или через `.lock().expect("...")`.
- `&format!(...)` → избыточные аллокации; где можно заменить на `&str`.
- Проверить обоснованность `#[cfg(debug_assertions)]` и `cfg!(debug_assertions)` — правильность использования.

**TypeScript / React:**
- Использование `useCallback` и `useMemo` — корректность зависимостей (проверить `handleOpenFile` в `useEffect`).
- `any` и нестрогие типы: проверить `onSave: (content: string) => void` в `EditorWrapper`, сигнатуры колбэков.
- Устаревшие паттерны: `useRef(getCurrentWindow().label)` — вызов функции в инициализаторе `useRef` (выполняется при каждом рендере, хотя значение используется только один раз).
- Асинхронные `useEffect` без cleanup — потенциальные утечки памяти при размонтировании.
- `import * as XLSX from 'xlsx'` — импорт всей библиотеки вместо tree-shakeable импорта.

### Вектор 3: Производительность и асинхронность

**Rust:**
- `Mutex<HashMap<...>>` для `OpenFiles` — блокировка всего реестра при каждой операции. Оценить `RwLock` или `DashMap`.
- `Mutex<u32>` для `WindowCounter` — избыточно, можно `AtomicU32`.
- Команды `read_file_content` / `write_file_content` синхронные (`std::fs::read_to_string`, `std::fs::write`) — при больших файлах блокируют поток Tauri. Оценить `tokio::fs` или `spawn_blocking`.
- `base64::Engine::decode` для `write_file_binary` — буферизация в памяти всего файла.

**TypeScript / React:**
- `editor.on('change', () => onSave(editor.getValue()))` в `EditorWrapper` — вызов на каждое нажатие клавиши. Оценить debounce.
- Рендеринг: `fileKey` для пересоздания `EditorWrapper` — проверить альтернативы (например, метод `editor.setValue()` без полного ремаунта).
- `handleExportDocx`: синхронный парсинг `currentValue.split('\n')` с линейным проходом — на больших документах блокирует UI. Оценить `requestIdleCallback` или Web Worker.
- Импорт XLSX/DOCX: `mammoth.convertToHtml` и `XLSX.read` выполняются в главном потоке.

### Вектор 4: Гигиена кода и технический долг

- **Мёртвый код**: `@types/html-to-docx` в `devDependencies`, хотя `html-to-docx` не используется (заменён на библиотеку `docx`). Упоминание `@m2d/md2docx` удалено, но проверить остаточные импорты. `vite-plugin-commonjs` в dependencies — используется ли?
- **Комментарии**: русские комментарии в `lib.rs` (строки 6, 11, 14, 72-73) — смесь языков в кодовой базе (менее критично, но неединообразно).
- **TODO/FIXME/HACK**: поиск маркеров технического долга.
- **Обработка ошибок (Rust)**: `let _ = window.show(); let _ = window.set_focus();` — молчаливое игнорирование ошибок. Где нужно логирование через `tauri-plugin-log` или `eprintln!`.
- **Обработка ошибок (TypeScript)**: `try { await writeTextFile(...) } catch { await invoke('write_file_content', ...) }` (строки 322-326) — fallback без проверки типа ошибки; любая ошибка `writeTextFile` вызывает `invoke`, что может маскировать настоящую проблему.
- **Зависимости**: `buffer` в `dependencies` — полифил, нужен ли в контексте Tauri 2 + Vite 8? `@types/markdown-it` в `dependencies`, а не `devDependencies`.
- **Статический анализ**: проверить отсутствие `eslint-disable`, `@ts-ignore`, `allow(unused)` без комментариев.

## Часть II: Макро-аудит — Архитектурное единство и стандартизация

### Вектор 5: Семантическое дублирование алгоритмов и утилит

Сравни Rust-бэкенд и TypeScript-фронтенд:

- **Нормализация путей**: `normalize_path` в Rust (`p.replace('\\', "/").to_lowercase()`) и `.split(/[\\/]/).pop()` в TypeScript — две разные реализации одной логики. Должна быть одна стратегия (либо на бэкенде с передачей нормализованного пути, либо единая утилита).
- **Извлечение имени файла**: `path.split(|c| c == '/' || c == '\\').last()` в Rust vs `currentFile.split(/[\\/]/).pop()` в TypeScript — дублирование.
- **Обработка путей**: `path.toLowerCase().endsWith('.md')` в TypeScript vs отсутствие проверок расширений в Rust.

### Вектор 6: Единообразие IPC-контрактов (Frontend ↔ Backend)

- **Два канала для файловых операций**: `plugin-fs` (`readTextFile`, `writeTextFile`) и кастомные Rust-команды (`read_file_content`, `write_file_content`). Какова стратегия? Всегда пробовать `plugin-fs` с fallback на Rust? Если да — формализовать в виде утилиты `safeReadFile` / `safeWriteFile`.
- **Консистентность команд**: `is_file_open` возвращает `Option<String>`, `focus_window` принимает `String`, `register_file` принимает `(String, String)`. Единый ли формат имён (snake_case vs camelCase в invoke)? Проверить нейминг.
- **Обработка ошибок IPC**: `invoke('...').catch(console.error)` — молчаливое проглатывание ошибок IPC в нескольких местах. Нужна единая стратегия (например, хук `useInvoke` с единым error boundary).

### Вектор 7: Стандартизация сквозных задач

**Управление состоянием:**
- Тема: `plugin-store` (persistent, async).
- Зум: локальный `useState` (не сохраняется).
- Файл: локальный `useState` + реестр в Rust (гибрид).
- Оценить единообразие: должны ли все persistent-настройки идти через `plugin-store`?

**Логирование и отладка:**
- Rust: `tauri-plugin-log` (только в debug), `eprintln!` отсутствует.
- TypeScript: `console.error` для ошибок, `console.warn` для mammoth messages.
- Нет единого логгера. Оценить внедрение `tracing` в Rust и структурированного логгера в TypeScript.

**Валидация:**
- Проверка расширений файлов: в `handleOpenFile` (`.md`, `.txt`, `.markdown`) и в диалогах `open()` (`['md', 'txt']`) — разные наборы расширений.
- Нет валидации содержимого (пустой файл, бинарный файл с расширением `.md`).

**Управление окнами:**
- `create_file_window` создаёт окна 800×600, а главное окно тоже 800×600 из `tauri.conf.json`. Есть ли консистентность? Дочерние окна не наследуют тему/зум — это баг или фича?

### Вектор 8: Контракты передачи данных

- **Типы IPC**: `invoke<string | null>('is_file_open', { path })` — generic-тип указывается вручную при каждом вызове. Нет централизованных типов для ответов команд.
- **Формат ошибок**: Rust-команды возвращают `Result<T, String>` — ошибка передаётся как plain string. TypeScript ловит через `catch (e)` и выводит `console.error(e)`. Нет структурированного error payload (код + сообщение + детали).
- **DTO для команд**: все параметры передаются как отдельные аргументы. Нет centralised command objects / request DTOs в TypeScript.

## Процесс выполнения

1. **Сканирование**: систематический обзор всех файлов в `<workspace>`, кросс-ссылки между Rust и TypeScript.
2. **Категоризация**: каждая находка строго в один из 8 векторов выше.
3. **Оценка серьёзности**:
   - `[Critical]` — баг, гонка данных, утечка памяти, падение приложения.
   - `[Warning]` — архитектурный запах, дублирование, отсутствие обработки ошибок.
   - `[Info]` — стилистика, нейминг, неиспользуемые зависимости.
4. **Оценки**:
   - **Часть I** — «Code Cleanliness Score» от 1.0 до 10.0 (качество кода).
   - **Часть II** — «Architecture Unification Score» от 1.0 до 10.0 (архитектурное единство).
   - **Итоговый Aggregate Score** — среднее взвешенное двух оценок.
